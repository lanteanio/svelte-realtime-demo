## [Unreleased]

### Added

- **Connection diagnostics on the e2e connection wait, plus a sweep probe.** `waitForWS` installs a probe for the duration of the wait that records the connection-status timeline and every WebSocket the page opens, including each socket's URL and how it ended; a timeout now reports that timeline instead of only naming the selector it gave up on. It also logs a `[ws-slow]` line for any connect that passes but exceeds 2000ms, so a run yields evidence about its slow tail rather than only about outright failures. The status timeline is sampled rather than observed because the navbar swaps the whole icon element between `Wifi` and `WifiOff` across a status change, and a `MutationObserver` bound to the old node would go deaf at exactly the transition worth seeing. The socket URL is what separates "the app never connected" from "the app's connection was ignored" - in dev the page also holds Vite's HMR socket, which opens immediately and never closes, and without the URL the two are indistinguishable. New `test/e2e/_ws-connect-probe.spec.js` (diagnostics tier) cycles the demo routes and reports the time-to-connected distribution, lost attempts, and per-route worst cases.

- **A multiplayer presence probe that measures convergence instead of asserting it once.** New `test/e2e/_mp-presence-probe.spec.js` (diagnostics tier) pairs two fresh browser contexts in the `live.multiplayer` room and waits for each to see the other, in a loop, reporting the failure rate with a Wilson interval and the convergence distribution among successes. On a failure it dumps both sides' rosters, because an empty roster cannot by itself distinguish a join that was never published from one delivered in only one direction, and those have different fixes. That capture is what identified the fault behind the intermittent gate failures: every failure is asymmetric, so the blind side's own join reached its peer while the peer's presence never arrived at all.

- **15 new demo pages - the gallery grows from 19 to 34, covering the full 0.6 primitive surface.** Each demo is one module in `src/live/demos/`, one page in `src/routes/demos/`, and one Playwright spec in `test/e2e/`: `collab-editor` (CRDT-anchored selections vs raw offsets on one shared `live.doc`), `multiplayer` (full-surface room: cursors, advisory locks, typing, reactions), `kanban` (shared CRDT board, zero RPC handlers), `offline` (IndexedDB-persisted mutation queue + idempotent replay), `arena` (`live.smooth({ interest })` area-of-interest culling with LOD bands), `shooter` (`live.smooth({ hitTest })` lag-compensated hits with a latency slider), `lobbies` (`live.room` browser with `meta`, ownership succession, and `shortCodes()`), `tenants` (`realtime({ tenant })` strict per-connection isolation), `flags` (`live.flag` cluster-replayed feature flags), `alarms` (Redis-durable `ctx.setAlarm` one-shots that survive restarts), `forget` (`live.forget` erasure with a per-surface audit), `privacy` (`live.aggregate` k-anonymity + differential-privacy hybrid), `ops` (`introspect()` dashboard), `outbound-webhooks` (`live.webhooks.outbound` sign / retry / dead-letter / replay), and `phases` (attach lifecycle + `ctx.batch` atomicity across an await boundary). The game demos keep their simulation in pure `.shared.js` modules shared verbatim by server and client. Two supporting API routes: `api/demos/webhook-sink` (HMAC-verified receipt sink) and `api/demos/set-tenant` (session tenant switcher). Homepage tiles carry a per-demo `since` badge; demos with persistent user content (`offline`, `tenants`, `flags`, `outbound-webhooks`, `phases`) register with the purge cron.

- **0.6 platform wiring: coordinators, admin plane, tenancy, protocol version.** `src/lib/server/redis.js` now constructs the full 0.6 coordinator set (CRDT cluster, smooth cluster, topic broadcast, alarm store, dead-letter store, retry budget, webhook breaker) inside `activateRedisInfrastructure()`, exposed via `redisCoordinators()` and torn down on shutdown. `src/hooks.ws.js` uses `realtime({ tenant, admin, protocolVersion })` as a config-only seam (the hand-rolled init/cron hooks stay authoritative) and exports `admin`, so the adapter mounts the fail-closed `/__realtime/*` plane (introspect, DLQ inspect + replay, lifeline metrics; bearer `ADMIN_TOKEN`, unset = deny all). Identity sessions gain an optional `tenant` field (`acme` / `globex`). `src/lib/protocol-version.js` pairs `realtime({ protocolVersion })` with the client's `configure({ protocolVersion })`; a tab whose baked bundle is older than the server gets a sticky `outdated` health state and the layout's reload banner. `svelte.config.js` sets `healthCheckPath: false` - the 0.6 adapter default `/healthz` would shadow the app's dependency-aware route - and pins the readiness probe at `/readyz`.

- **Versioned database migrations replace `schema.sql` and runtime DDL.** Ordered, checksummed SQL files under `migrations/` are applied by `scripts/migrate.mjs` (`npm run migrate`) under a Postgres advisory lock, recorded in a `schema_migration` table, and re-verified by checksum on every run. A `migrate` compose service runs them pre-traffic (the `app` service waits on `service_completed_successfully`), and `deploy.sh` applies them before starting replicas. Runtime request/worker startup performs no DDL anymore: the `ALTER TABLE` bootstrap in `hooks.server.js` is gone, and startup only ensures well-known application data exists.

- **Readiness endpoints.** `GET /healthz` returns structured per-dependency readiness (`postgres` including applied-migrations check, `redis`, with bounded probe budgets via `READINESS_TIMEOUT_MS`) as 200/503 JSON; a per-container Unix-socket probe (`$lib/server/local-health` + `scripts/container-healthcheck.mjs`) backs the Docker `HEALTHCHECK` without traversing the public listener. `deploy.sh` and the new `scripts/deployment-smoke.mjs` gate rollouts on it.

- **Redis failure-domain isolation.** New `$lib/server/redis-breakers` supplies separate circuit breakers for the realtime infrastructure and the identity-session store, so session-store failures cannot open the realtime breaker (and vice versa); session reads/writes are bounded by `REDIS_SESSION_TIMEOUT_MS`. `$lib/server/redis-options` bounds command retries, initial-connect attempts, and reconnect backoff so no Redis call can hang a request indefinitely. `$lib/server/redis-command-safety` observes every command promise so extension-owned fire-and-forget commands (timers, reconnect paths) cannot terminate the worker as unhandled rejections.

- **Note-move buffering extracted to `$lib/server/note-buffer`.** The per-note write-behind cache from the boards module now lives in its own unit-tested module with generation-tracked merges: a buffered position always survives a concurrent DB read, a failed flush leaves the entry dirty for retry, and a move that races a flush keeps the newer position. During a Postgres outage, moves on a warm note keep publishing and the last position flushes durably once Postgres returns (covered by the new `e2e/resilience.spec.js`).

- **CI and a unit-test tier.** GitHub Actions workflow runs `npm ci`, `npm audit --audit-level=high`, and `npm test` (unit tests + the safe e2e tier) on Node 22.19. New `tests/unit/` suite covers the advisory lock, note buffer, breakers, Redis options and command safety, e2e target validation, and field validators. Local runners: `npm run test:unit`, tiered e2e via `scripts/run-local-e2e.mjs` (`safe` / `main` / `isolated` / `cluster` / `resilience` / `stress` / `destroyer` / `diagnostics` / `complete`), and `npm run check` (svelte-check + syntax sweep of every shipped .js/.mjs).

- **Deployment pipeline hardening in `deploy.sh`.** Images are tagged with the exact git revision (rollback never relies on a mutable `latest`), the Linux entrypoint is byte-smoke-tested before rollout, migrations run pre-traffic, and a failed rollout automatically rolls replicas back to the previous image (`docker-compose.rollback.yml` disables the image-local healthcheck so older images can restart) and re-verifies the site with an external smoke check (readiness + page + WebSocket upgrade). The certbot service now also verifies the served certificate after each renewal (`scripts/verify-served-cert.sh`); transient renew/verify failures log and retry at the next 12h interval.

- **E2E target safety.** `scripts/test-target.mjs` rejects non-loopback E2E targets unless `ALLOW_REMOTE_E2E=1` is set explicitly, so a stray `BASE_URL` can no longer point the destroyer or stress suites at production by accident. Shared WS RPC helpers moved to `e2e/ws-rpc.js`.

- **Destructive demo controls ask first.** Eleven controls wipe state that every visitor of a public demo shares (`checkout` reset, `collab-editor` clear document, `counter-resume` reset, `effect` clear feeds, `flash-sales` reset sale, `forget` erase, `jobs` clear, `pressure` clear shed log, `schema-evolution` reset, `todos-rollback` clear all, `upload` clear files). Each now routes through `$lib/confirm-destructive`, which appends one shared warning to a caller-supplied question, and each moved from `btn-ghost` to `btn-outline btn-error` so the dress matches the consequence. The e2e suite gained `confirmAndClick` / `dismissConfirmation` helpers that assert the dialog's type and text, so a control that silently loses its gate fails loudly instead of being auto-dismissed into a no-op.

- **`/demos/from-seq` can reach its third tier without a 200-second wait.** The reconnect ladder is replay buffer -> `delta.fromSeq` -> loader rehydrate, but the Redis replay buffer never reports a miss, so `delta.fromSeq` was unreachable in this app and a visitor had nothing to look at. A new "Arm fast fromSeq" control subscribes to a demo-scoped parallel stream whose adapter replay seam deliberately reports a bounded-buffer miss, so a two-second pause exercises the real `delta.fromSeq` bridge. The production stream keeps its unchanged three-tier behavior; the fast stream carries its own durable sequence domain, and its bridge returns a miss (falling through to the loader) whenever the resume cursor lies outside the window its store can actually answer for, rather than returning a confidently wrong slice.

- **`/demos/arena` shows the boundary it is about.** The viewport grew from 640x420 to 900x600 so the 420-unit cull rim and the complete 300-unit LOD ring are both on screen, with both drawn as camera-centred rings plus a legend; the old view sat entirely inside the cull circle, making the demo's defining boundary invisible. Touch devices get a d-pad that feeds the same held-direction set the keyboard uses, so a held button moves continuously and diagonals work.

- **Operational env knobs (all optional).** `DATABASE_POOL_MAX` (default 10), `DATABASE_CONNECT_TIMEOUT_MS` (2000), `REDIS_SESSION_TIMEOUT_MS` (1000), `READINESS_TIMEOUT_MS` (2500), documented in `.env.example`. `.nvmrc` and an `engines` floor pin Node >= 22.19.0; `.gitattributes` normalizes line endings.

### Changed

- **BREAKING (local e2e): every tier now runs the production build, never `vite dev`.** `scripts/run-local-e2e.mjs` builds once and starts `build/index.js` for all tiers; the dev-server path and `startApp`'s `production` parameter are gone. Debugging against the dev server is still possible by running `npm run dev` and pointing Playwright at it through `BASE_URL`. Two reasons. First, the dev server intermittently failed to hydrate a page: the SSR HTML rendered, Vite's own HMR socket connected, and the app bundle never booted, leaving the page with no app socket, no pending retry, and a connection status still on its initial value - so it never recovered at any timeout, and the gate reported a `waitForWS` failure against a page whose JavaScript never ran. Measured at roughly one open in 900 while cycling routes, and zero in 80 opens of a single warm route, which is why re-running a failed spec in isolation always "passed" and cleared code that was never at fault. Second, and larger: the demo serves WebSockets through `svelte-adapter-uws/vite` in dev and through the adapter's production handler when built, so every tier except `stress` and `destroyer` had been validating a WebSocket implementation that is never deployed.

- **The local e2e harness reclaims containers left by runs that were killed.** `scripts/run-local-e2e.mjs` removes its Postgres and Redis containers in `cleanup()`, which covers a normal exit and SIGINT/SIGTERM but not a harder kill, and nothing else ever reclaimed them: eight were found still running, the oldest 29 hours old, alongside 677 dangling volumes holding about 16GB. The sweep now runs at STARTUP, the only placement that survives a kill, and keys on the creating PID that the container name already carries, so a container whose owner is gone cannot have a live one. A recycled PID reads as alive and its container is left alone, because concurrent harness runs are legitimate and deleting a running tier's database is far worse than leaving a leak in place. Container removal also passes `--volumes` now, so the anonymous volume goes with the container instead of accumulating invisibly. Selection logic lives in `scripts/orphan-sweep.mjs` with unit coverage, since `run-local-e2e.mjs` runs its whole pipeline on import and anything left inside it is reachable only by running a full tier.

- **BREAKING (local scripts): lean-root restructure.** The eight root shell scripts moved to `scripts/` (`deploy.sh`, `entrypoint.sh`, `init-app-role.sh`, `init-certs.sh`, `renew-certs.sh`, `reset-all.sh`, `reset-db.sh`, `reset-redis.sh`; each now `cd`s to the repo root itself), and the test trees moved to `test/e2e` (was `e2e/`) and `test/unit` (was `tests/unit`). Anything invoking the old paths - shell history, local aliases, external runbooks - needs the new prefix. Playwright config, unit runner, `jsconfig.check.json`, `.dockerignore`, the Dockerfiles, and the README all reference the new layout.

- **The demo gallery chrome learned the new demos.** The homepage catalog and the `/demos` sidebar register all 34 demos; tiles show a per-demo `since` version badge. `/demos/pressure` renders the 0.6 pressure payload (PSI `cpuSome10`, cgroup `throttledRatio`, `maxBufferedBytes`, `backpressuredConnections`) alongside the scalar. The topic registry (`src/lib/server/topics.js`) covers every new demo topic and the new modules reference it, keeping it the single source of truth for the wire namespace.

- **Bumped the realtime stack to the 0.6.0-next lines: `svelte-realtime` `^0.6.0-next.88`, `svelte-adapter-uws` `^0.6.0-next.75`, `svelte-adapter-uws-extensions` `^0.6.0-next.52`.** These tips carry the fixes a full demo e2e pass surfaced across several rounds. The first round cleared the build blocker and SSR crashes: the adapter crdt client codec no longer drags server `node:` builtins into the browser bundle, realtime's SSR stubs gained the `live.flag` set-merge readable and the multiplayer `room().bindDoc` method, and extensions' `presence.purgeUser` no longer throws on a topic-level observer refcount (unblocks `live.forget`). The later `.75`/`.88` tips fix runtime races a full pass then surfaced: the adapter client reacts to browser `online`/`offline` events so the offline-queue demo arms without waiting for a ping timeout; `live.smooth({ onTick })` arms its tick on a bare subscribe so server-driven entities animate for a watching-but-idle client (`arena` / `shooter`); a `live.room({ owner: true })` first joiner reliably receives the ownership its own join claimed; and room presence plus enumerable counts now converge and release across replicas on a live-socket unsubscribe. Because this app owns the adapter `unsubscribe` hook, it now chains realtime's managed-topic drain before the extensions presence cleanup; the lobbies cluster regression is a normal green assertion again. The 0.6 extensions stamp `user_id` (and `tenant_id` on idempotency rows) into the durable jobs stores so a user's rows can be purged; the demo's `demos_jobs_*` tables run `autoMigrate:false`, so migration `003_demo_jobs_erasure_columns.sql` carries the same forward-only ALTERs.

- **The `/demos` rail now appears at 1024px instead of 640px.** A fixed 13rem sidebar from 640px up meant every child page's `sm:` and `md:` breakpoint described a width the content column did not have, so responsive rules fired against a lie. Keeping the 640-1023px band rail-free makes those breakpoints honest; the switcher renders as a horizontal strip below 1024 and the active entry is scrolled into view within the nav's own scroll container (never the document). Child pages whose three-up rows fired exactly where the rail returns moved out to the next band. Sidebar titles were also reworded so the entry, not the primitive, leads.

- **`/demos/upload` describes `live.notify` accurately.** The page and module claimed the upload notification fanned out to "every other tab the same user has open". `live.notify({ userId }, ...)` targets the user's most recently connected socket, locally and through the cluster registry - last-write-wins, not fan-out. Copy, headings, and the closing explainer now say that. Re-uploading a file is also an upsert rather than a second logical entry, since ids are content-addressed: the record, its order-list position, and the byte counter move together in one Redis turn.

- **`editNote` accepts only `content` and `color`; position fields moved exclusively to `moveNote` / `focusNote`.** The note buffer owns x/y during a drag (a buffered position always wins over a DB read), so an `editNote` position write would be published and then reverted by the next flush. `validateNoteFields` drops `x` / `y` / `z_index` from the edit allowlist; a position-only `editNote` payload now returns a VALIDATION error. All in-repo callers already used `moveNote` / `focusNote`.

- **`npm run build` wraps vite via `scripts/build.mjs`.** SvelteKit's post-build analysis imports server chunks under `NODE_ENV=production`, which would trip the fail-closed webhook-secret check on machines without the real secret; the wrapper supplies an analysis-only placeholder while production startup still reads its own environment. `svelte-check` runs against a dedicated `jsconfig.check.json`.

- **`/demos/pressure` labels its publish-rate source.** Production reads the adapter's pressure snapshot as before; `vite dev` (where the dev platform reports a zero snapshot) falls back to a demo-side generated-load counter and the payload says which source produced the number, so the readout is never silently wrong in dev.

### Changed

- **Removed `websocket.compression` from `svelte.config.js` (was `1` = SHARED_COMPRESSOR; now omitted, reverts to uWS default `0` = DISABLED).** Empirical: enabling permessage-deflate at 1000-cursor stress on Hetzner CCX13 saturated both modes -- SHARED_COMPRESSOR=1 because all 1000 subscribers serialized through one deflate context, and DEDICATED_COMPRESSOR_3KB=9 because per-connection contexts at scale fan-out to ~1000 simultaneous compress operations per cycle. In both cases, TLS handshake latency climbed from ~100ms to 8+ seconds during sustained load, and the e2e harness declared the demo unresponsive across 7 of 8 shards. The bandwidth win compression promises is not worth the CPU cost on a 2-vCPU box at this connection count. Wire-byte reduction at this scale belongs at the wire-format layer, not in deflate.

- **Bumped `svelte-adapter-uws` from `^0.5.6` to `^0.5.8` and `svelte-adapter-uws-extensions` from `^0.5.7` to `^0.5.9`.** Two coordinated upstream changes consumed in this bump. **(1) Presence diff + relay batching via `setTimeout(0)` (adapter 0.5.8, extensions 0.5.9).** Same bug class the 0.5.6 cursor always-tick rewrite fixed -- `bufferDiff` in `redis/presence.js` and the cross-worker relay scheduler in `redis/pubsub.js` / `redis/sharded-pubsub.js` previously deferred their batched flush via `queueMicrotask`, which drains between WS dispatches in uWS's per-socket task model. Mass-join into a populated presence topic produced O(N) one-entry diffs instead of one batched per topic; the demo's cap probe at 8000 ws measured ~800 KB/conn outbound buffer accumulation vs the steady-state ~40 KB/conn linear curve. `setTimeout(0)` lands in libuv's timers phase after the poll phase has dispatched every ready socket message, so all co-arriving joins coalesce into one diff per topic. **(2) BREAKING: presence wire event names renamed `presence_state` -> `state`, `presence_diff` -> `diff` (adapter 0.5.7, extensions 0.5.8).** The `__presence:` topic prefix already namespaces the channel, so the redundant `presence_` event-name prefix was dropped to match the wire shape of cursor (bare `catalog`/`update`/`bulk`/...), groups, and replay. **Breaking only for hand-rolled wire decoders;** the bundled `presence()` Svelte store (which the demo uses for both `presence('global')` and `presence('board:UUID')`) updates in lockstep, so the demo's callers are unaffected. Prometheus metric names (`presence_diff_frames_total`, `presence_diff_coalesced_total`) are unchanged -- they are Prometheus-side identifiers, not wire events. See respective package CHANGELOGs for full mechanics.

- **Bumped `svelte-adapter-uws` from `^0.5.5` to `^0.5.6` and `svelte-adapter-uws-extensions` from `^0.5.6` to `^0.5.7`.** Supersedes the 0.5.5 / 0.5.6 `queueMicrotask` defer for cursor leading-edge fragmentation. The microtask defer assumed co-arriving broadcasts share a JS task -- they don't: uWS dispatches each WS message as its own task and microtasks drain between dispatches, so the deferred flush fired BEFORE the next socket's handler ran. Demo verification at 1000-mover load on Hetzner CCX13 measured ~99% UPDATE / ~1% BULK under 0.5.5+0.5.6, essentially identical to the pre-fix shape -- per-cursor effective rate still ~0.14 Hz against the 125 Hz target. The always-tick rewrite drops the leading-edge sync fire AND the microtask defer; every `broadcast()` (and `enqueueInbound()` in the cluster path) queues into `dirtyTopics` and arms the tracker-wide `tickTimer`. The `setTimeout(0)` arm fires after libuv's poll phase processes every ready message on every socket, so flushBoth sees the fully-accumulated dirty map from all source sockets in the same event-loop iteration. Cost: up to `topicThrottleMs` of latency for the first message on an idle topic (acceptable at 8-16 ms cursor cadence); benefit: structurally correct independent of dispatch model. Both fixes ship together because extensions 0.5.7 requires adapter `^0.5.6`. See respective package CHANGELOGs for full mechanics.

- **Bumped `svelte-adapter-uws` from `^0.5.4` to `^0.5.5`.** Two production-stress fixes filed against the demo during the 1000-cursor smoothness investigation. (1) **`platform.*` closed-WS race.** `platform.subscribe`, `unsubscribe`, `send`, `sendCoalesced`, `sendTo`, and `request` previously threw uWS's `"Invalid access of closed uWS.WebSocket"` when the underlying socket closed during an awaited gate (e.g. the user-subscribe hook chain). Uncaught -> worker exit -> Docker restart -> hundreds of subscribers dropped per cascade. Adapter now swallows the throw, returns a success-shaped no-op sentinel, and bumps a new `platform.closedWsAborts` counter so operators can detect drop frequency. The demo's stress run was crashing `app-3` deterministically under mass-connect on the 2-replica deploy; this fix eliminates the cascade. (2) **Cursor `topicThrottle` leading-edge fragmentation.** `broadcast()` in `plugins/cursor/server.js` now defers the leading-edge flush by `queueMicrotask`, so cursors co-arriving in the same JS pass batch into one bulk frame instead of fragmenting into one single-cursor UPDATE + N-1 trailing entries. The demo's smoothness probe pre-fix measured 1794 UPDATE / 38 BULK (86% fragmentation) over 30s at 1000-mover load; per-cursor effective rate collapsed to 0.14 Hz against a 125 Hz target. Adapter microbench (100 bursts x 250 cursors) post-fix: 0 UPDATEs / 100 BULKs of exactly 250 entries each. See `svelte-adapter-uws` CHANGELOG for full mechanics.

- **Bumped `svelte-adapter-uws-extensions` from `^0.5.4` to `^0.5.6`.** Two coordinated fixes mirroring the adapter 0.5.5 work. (1) **`presence.join` + `cursor.attach` throw `WsClosedError` instead of silently undoing.** Pre-fix, both functions detected a closed WS after `await subscribeToTopic` (via the `getBufferedAmount` probe) and returned silently after state rollback; the calling `live()` wrapper saw no error and reported the RPC as `status="ok"`. Under mass-connect, 10-15% of `boards/cursors/joinBoard` RPCs were silently dropped this way -- the metric lied. Now throws `WsClosedError` (stable code `'WS_CLOSED'`, re-exported from both modules) so the RPC metric labels these as errors and callers (including `PresenceBar.svelte`'s retry path) can branch on the cause. Adds `presence_joins_aborted_total{topic,reason}` and `cursor_attaches_aborted_total{topic,reason}` for fleet visibility. (2) **`redis/cursor.js` mirrors the adapter's microtask-deferred leading-edge** for the cluster path, including `enqueueInbound()` for peer-relayed cursors. `cursor.attach` switches to raw `ws.subscribe` so the WsClosedError throw contract survives adapter 0.5.5 swallowing uWS throws at the platform layer (without this switch, both branches return null and the caller can't distinguish closed-WS from success). Peer dep floor bumped to `svelte-adapter-uws ^0.5.5`. See `svelte-adapter-uws-extensions` CHANGELOG for full mechanics.

- **Bumped `svelte-adapter-uws` from `^0.5.3` to `^0.5.4`.** Cursor flush scheduler rebuilt: per-topic `setTimeout` (which compounded drift under load because `lastFlush` was anchored on actual fire time, pushing every subsequent cycle's deadline) replaced with one tracker-wide `tickTimer` aimed at the next earliest topic deadline; `lastFlush` now advances by `topicThrottleMs` (target-anchored), so a late fire affects exactly one cycle and a multi-cycle backlog under saturation collapses to `now` instead of producing phantom catch-up fires. The demo's smoothness probe measured per-worker fan-out at ~50Hz against a `topicThrottle: 8` (125Hz) target on the CPX22 deploy pre-fix; the target-anchored scheduler restores intended cadence under saturating incoming RPC load. Adds a `stats()` accessor on the cursor tracker returning `{flushes, driftMeanMs, driftMaxMs, dirtyTopicsCurrent, activeTopicsTotal}` -- always-on, near-zero cost -- so operators can detect sustained event-loop saturation (`driftMeanMs > topicThrottle`) or GC pauses (`driftMaxMs` spikes vs. mean) from a single call. Also soft-flips the presence server `heartbeat` default from `0` (disabled) to `30000` (30s) and the client `maxAge` default to `90000` (3x safety); this demo already sets both explicitly (`src/lib/server/redis.js` and the presence-store callers), so no behavior change here. See `svelte-adapter-uws` CHANGELOG for full mechanics.

- **Bumped `svelte-adapter-uws-extensions` from `^0.5.3` to `^0.5.4`.** Cluster cursor smoothness fix. Pre-fix, each uWS worker emitted both its own local cursor flush AND immediately republished peer-relayed cursors (received via the Redis pub/sub channel) as a separate frame, so any single subscriber saw tight doublets per cycle. The demo's smoothness probe at `e2e/_smoothness-probe.spec.js` measured `p50 = 0ms` inter-frame intervals with 38% of those tight (<3ms) pairs carrying keys from a different worker's `instanceId` than the previous frame -- the cross-replica double-emit pattern, observable as jitter on 120Hz displays and doubling outbound bytes per subscriber. Post-fix, the Redis subscriber handler in `redis/cursor.js` routes inbound `update` / `bulk` frames into a per-topic `inboundDirty` map; the next local flush emits one combined frame covering local + peer cursors. The relay payload remains the local-origin slice only -- re-relaying received cursors would loop (filtered at receiver, but wastes pub/sub bandwidth `O(worker_count)`) and would double the `queueSnapshot` HSET storm (origin owns the HSET). `catalog` / `join` / `remove` bypass aggregation: low-frequency roster events where latency matters more than smoothness. Mirrors the matching scheduler rebuild + `stats()` accessor from the adapter (above). Rolling-deploy safe: old worker still emits the legacy doublet pattern for subscribers on new workers; full benefit when every worker is on `^0.5.4`. See `svelte-adapter-uws-extensions` CHANGELOG for full mechanics.

- **Bumped `svelte-realtime` from `^0.5.3` to `^0.5.4`.** 0.5.4 closes the dev-mode publish-rate-sampler retention leak via WeakRef + per-process epoch; sampler self-clears when its captured platform is GC'd or when reset / disable bumps the epoch. The demo's `docker-compose.yml` already sets `NODE_ENV=production` so the dev path is dead in this deployment regardless, but the framework fix means a future deploy with a missing `NODE_ENV` (or anyone running locally in dev) no longer leaks. See the framework CHANGELOG for full mechanics.

### Fixed

- **Board presence stopped sticking at "1 here" after the last member left.** The board list renders a presence badge per board, and the Redis presence extension treats any subscribe to a non-`__presence:` topic as a member JOIN - so every card observing a board's roster was counted as a member of it. `PresenceBar` already owns the real lifecycle (join on mount, leave on cleanup), so the app's subscribe hooks now skip the plugin join for the bare `board:<id>` topic and let the observer path authorize through `platform.checkSubscribe` instead. Sub-topics (`:notes`, `:settings`, `:activity`) and socket close are unaffected.

- **Lobby rosters and owner succession release on an explicit unsubscribe.** This app owns the adapter's `unsubscribe` hook, which REPLACES the framework's rather than composing with it, so realtime's managed-topic drain never ran on a wire unsubscribe and only fired at socket close: a visitor who left a table stayed on its roster, and an owner who left never handed the room on. The hook now chains `unsubscribe` from `svelte-realtime/server` before the extension's presence cleanup. Note one upstream consequence, filed against the framework: realtime records drained topics per socket and does not clear that record when the same socket re-subscribes, so a leave-rejoin-close cycle on one connection skips the close-time drain. The demo's own regression coverage exercises that path.

- **`/demos/arena` reported "of 0 entities" on non-authority replicas.** The HUD denominator came from a module-level cell written by the smooth authority's tick, but `SO_REUSEPORT` gives no guarantee that a page's RPC lands on the process running the authority, so three replicas out of four answered zero. The tick mirrors catalog-size changes into Redis and the RPC reads the shared value, cached for a second per process so a polled HUD line does not become one Redis round trip per open tab, and falling back to the local cell rather than surfacing an infrastructure error if the read fails.

- **Re-uploading an identical file no longer double-counts its bytes or strands an order entry.** Ids are content-addressed, so the second upload of the same file appended a duplicate list entry and added its size to the shared byte counter again, permanently inflating the total against the 50 MB cap. Append and remove are each one atomic Redis script now, as is each eviction step - previously a replica that read a record just before another replica removed it still subtracted its bytes, and once the counter went negative the byte cap stopped being enforced and the page rendered a negative total. The stale counters repair themselves on the next append or removal. The page's notification list is also keyed per notification rather than per file, so a repeat upload cannot collide with itself and blank the banner.

- **`/demos/privacy` no longer claims to have published when it has not.** The protected aggregate's initial serve is an un-noised zero seed, and the wire cannot distinguish that from a real held value, so a pristine server rendered `0.00 (last published value)` for a publish that never happened. The round RPC reports whether this process's aggregate has actually crossed k, and the card holds until it says so. The flag is deliberately per-process, matching the lifetime of the in-memory aggregate state it describes: a cluster-wide durable flag would outlive that state and tell a restarted replica's visitors "published" while showing them the seed.

- **`/demos/chaos` no longer mixes two runs in one strip.** A new run restarts tick ids at 1, and with a keyed CRUD merge those rows overwrote the previous run's in place while its later rows survived - so the tick counter, delivered count, and empirical drop rate were read off a stale row until the new run reached 60 ticks. Starting a run now refreshes the stream first.

- **`delta.fromSeq` results actually merge.** A `delta.fromSeq` bridge must return `{ event, data, seq }` envelopes: a `replay: true` array response is fed straight into the client's merge, which dispatches on `envelope.event`. The from-seq demo returned bare rows, which carry no `event` and silently applied nothing - the tier had never rendered a row.

- **Readability and layout fixes across the gallery.** The navbar's end cluster no longer paints over the wordmark between 640 and 1023 (the online count and colour picker wait for `lg`), and the wordmark truncates rather than being covered. Demo explainer asides were 12px at 50% opacity - about 3.4:1 on light, under the AA bar - and now render at 14px / 70%. The board canvas empty-state hint derives its ink from the board's own background rather than the theme, at an alpha that clears 4.5:1 on all six palette values. Hostile board titles truncate instead of widening the page (and the create field caps at the length the server already enforced). Plus per-page fixes at phone and tablet widths: the chaos decision strip fits 60 cells at 320px, pagination rows wrap and confirm an append through a live region, the pressure shed log scrolls instead of clipping its reason column, `flash-sales` stock badges stop being clipped, `lobbies` inputs carry real labels, and `tenants` shows the effective wire topic.

- **`/demos/offline` demonstrates itself without DevTools.** A first-time viewer on a live connection saw the queue stay 0 and nothing of the offline -> reconnect -> dedup story, because the interesting behavior only happened if you manually toggled DevTools offline. Added an in-page **Go offline / Reconnect** toggle (plus a live offline/online banner and guiding copy): it drops the live socket - the same transition that arms the realtime queue - and blocks reconnection with a temporary `window.WebSocket` stub until Reconnect, so posts made in between queue in IndexedDB and replay exactly once on reconnect, visibly, in one click. Uses only supported client behavior (the adapter client already drops on the browser `offline` event and reconnects on `online`); `maxReconnectAttempts` defaults to Infinity, so the blocked reconnect loop can never wedge into a terminal state, and the block is torn down if the viewer navigates away mid-simulation. A new `demos-offline.spec.js` case drives the toggle end to end (queue two posts, reconnect, each lands exactly once). This is a demo affordance; a first-class client-side simulate-offline primitive is the proper long-term home.

- **`/demos/ops` now names the replica it read.** `introspect()` is per-process by design (registry sizes, connection count, cron-running, RSS are all local to one worker), so on the SO_REUSEPORT cluster each reconnect can land on a different replica and the counts swing between refreshes - correct behavior that read as "is this broken?" on a showcase. The snapshot RPC now stamps `replica: leader.instanceId` (the same worker id `/demos/cluster-cron` shows), and the page renders "reading replica X" beside the refresh time plus a one-line note that the numbers are per-worker. `leader.instanceId` is the extensions leader-lease identity; it is null only before init / during build analysis, in which case the readout is hidden.

- **`/demos/multiplayer` headline now commits the typed value.** Clicking the Set-headline button blurred the input, which flipped `editing` false and let the "mirror the live headline into the draft" effect overwrite the just-typed text with the current (default) headline before the submit handler read it - so the RPC published the default. The submit button now suppresses the focus steal (`onmousedown` preventDefault), so the input keeps focus through the submit and the draft survives.

- **Demo purge crons now actually run (they never had).** The general (every 30 min) and upload (every 5 min) purge crons lived in `src/lib/server/demo-purge.js`, outside `src/live/` - the only tree the realtime codegen scans to emit the cron registry - so `live.cron()` attached its schedule but nothing ever registered or ticked it. Weeks-old chat and other demo content accumulated in prod as a result. Moved both crons into `src/live/_purge.js` (registered form: `export const X = live.cron(...)` with the env kill-switch enforced in the handler instead of a ternary the codegen regex would not match); the boot-time eager demo import moves with it. Defense in depth: chat room LISTs now carry a 2h backstop TTL refreshed on each push (`src/live/demos/chat.js`), so an abandoned room self-expires even if a cron regresses. Regression guard: `npm run check` now fails if any `live.cron(` is defined outside `src/live/` (`scripts/check-cron-registration.mjs`). Verified: the built registry emits `__registerCron("_purge/purgeAllDemos")` / `purgeUploadCron`, and a 1-minute-interval production run logs `[demo-purge] tick at ... (failed=0)`.

- **`/demos/multiplayer` reactions no longer snap back to spawn or revive on each tap.** The reaction bar rendered the server's bounded reaction ring keyed by object identity (`{#each room.reactions as r (r)}`). Every push re-keyed the whole list, so Svelte tore down and rebuilt every emote node and restarted the float animation: emotes already floating snapped back to their spawn point and already-faded ones reappeared. The page now reconciles the ring into a locally-keyed list - a stable id per genuinely-new frame, dropped on a timer once its animation has run - so a tap appends exactly one emote and leaves the others floating undisturbed. A new `demos-multiplayer.spec.js` case guards it by asserting the first emote's float animation keeps advancing across a second, different tap instead of rewinding toward zero.

- **`/demos/kanban` board survives a reload.** The document declared no `persist` hooks on the assumption that the in-memory server replica lives for the process lifetime; in fact the framework releases a document's replica once its last subscriber disconnects, so a lone visitor's reload reset the whole board. Added a Redis snapshot `persist` (24h TTL, same shape as `/demos/collab-editor`), which also bounds the previously-unbounded public board.

- **`/demos/flags` reads the flag stores directly again.** With the realtime SSR flag stub now published, the page dropped its `onMount` + manual-subscribe workaround and reads `$banner` / `$darkLaunch` straight off the stores.

- **Page-local `configure()` calls no longer drop the app-wide client options.** `configure()` replaces the realtime client config wholesale, so the upload page's `configure({ upload: { frameSize } })` silently un-set the resume-grace window and the protocol version the root layout had established (the offline page worked around it by re-asserting both inline). New `$lib/configure-app.js` exports `configureApp(options)`, which merges the app defaults under the page's options; the layout, the upload page, and the offline page all go through it now.

- **`docker-compose.yml` sets `NODE_ENV=production` for the `app` service.** Pre-fix, the container had `NODE_ENV` unset; Node read it as `undefined`. svelte-realtime gates its dev-only publish-rate-warning sampler on `process.env.NODE_ENV !== 'production'` (treats anything other than `'production'` as dev). With the gate open, every call to `_getCtxHelpers(platform)` armed a `setInterval` for that platform and registered the platform in a strong-reference `Set` (`_publishRateActivePlatforms`). Combined with the cron tick's per-fire `bus.wrap(_cronPlatform)` minting a fresh wrapped platform every second on the leader, the Set accumulated one entry per fire at ~7 Hz across the news / topk / cluster-cron / notifications / pressure crons. Each retained entry kept the wrapped platform's full helpers + getters + an active timer alive. Heap grew by ~100 MB/hour on the leader worker until OOM. Setting `NODE_ENV=production` constant-folds the dev branch dead and the leak path stops at boot. Existing `bus.wrap`, `_getCtxHelpers`, and `_publishRateActivePlatforms` shapes upstream are unchanged; this fix is purely an environment correction. (Defense-in-depth follow-up belongs upstream in svelte-realtime: `_publishRateActivePlatforms` should be a `WeakSet`, not a `Set`, so a forgotten `NODE_ENV` cannot leak in dev either.)

- **`src/lib/server/upload.js` chunks Map switched to a Set of hashes only; bytes are no longer retained.** Pre-fix, every uploaded chunk's raw `Uint8Array` (up to 1 MB) stayed in a module-level `Map<hash, Uint8Array>` until `purgeMemory()` cleared it. Purge runs on a leader-gated cron, so non-leader workers in a clustered deploy never cleared their local Map and the Map grew without bound at upload rate. Bytes were also never read back (the demo's wire surface returns dedup metadata only; `getChunk` was exported but had no callers). The new shape keeps only the hash strings (Set membership for dedup checks), which is bounded at `MAX_FILES * avg-chunks-per-file` entries (~KB total). Removed the unused `getChunk` export; `storeChunk(hash)` no longer accepts the bytes argument.

- **`/demos/chaos` `states` Map now cleared on WS close.** Pre-fix, the demo's per-user state Map (`states: Map<userId, ...>`) was documented as "demo accepts the leak": every user who ran `startChaos` and disconnected without clicking Stop left an orphan entry that the 100ms ticker iterated forever, publishing into a topic with no subscribers. Anonymous demo users get a fresh `ctx.user.id` per session, so orphans accumulated one per session. Added an `onClose(ws)` export wired from `src/hooks.ws.js` close handler that calls `states.delete(ws.getUserData().id)`. Same fix shape that other in-process demo state should use; chaos was the only such demo.

- **`docker-compose.yml` now plumbs the 0.6 env vars into the `app` container.** The compose `environment:` block never forwarded `ADMIN_TOKEN`, `DEMO_OUTBOUND_WEBHOOK_SECRET`, `ROOMS_CODE_SECRET`, or `SSL_WATCH`, so values set in the operator's `.env` never reached the app process (Compose only forwards keys it interpolates). The most visible effect: the fail-closed `/__realtime/*` admin plane read `env.ADMIN_TOKEN` as unset and denied every request, including a correct bearer. All four are now forwarded as `${VAR:-}`, so `.env` values flow through and unset stays a safe default (admin plane fail-closed, optional secrets on their dev fallbacks).

- **TLS hot-reload (`SSL_WATCH`) defaults off for the host-networking deployment.** `svelte-adapter-uws` next.75 defaults `SSL_WATCH=1` - a restartless in-process cert reload that swaps the served cert as a uWS SNI server name. Under this stack's `network_mode: host` + SO_REUSEPORT layout that swap leaves the listener refusing external TLS handshakes (clients see the connection closed mid-handshake), even though the process logs a successful `:443` bind. Renewal here is already restart-based (certbot + `entrypoint.sh` graceful-restart on a fingerprint change), so the adapter watcher is redundant; `docker-compose.yml` and `.env.example` default `SSL_WATCH=0`. (Upstream follow-up: the adapter's SNI-swap reload should coexist with host-networking clustering so `SSL_WATCH=1` is safe there.)

### Security

- **App connects to Postgres as the non-superuser `stickynotes_app` role.** Pre-fix, the demo's `DATABASE_URL` connected as `postgres` - the superuser bootstrap role created by the official postgres image. An RCE landing inside the node container had full DDL / role-management / cross-database access from the connection it already held. Fix: a new `init-app-role.sh` runs once on first postgres init (via `/docker-entrypoint-initdb.d/00-init-app-role.sh`) and creates the `stickynotes_app` role with the password from `STICKYNOTES_APP_PASSWORD`. `schema.sql` runs a `SET ROLE stickynotes_app` block so the `board` / `note` tables, the `note_board_id_idx` index, and the `archive_old_notes()` function are all owned by `stickynotes_app`. Owner privilege lets the runtime `ALTER TABLE` in `hooks.server.js` continue to work without granting the app role broader rights. The role is NOT a superuser (`rolsuper=f`), cannot create other roles (`rolcreaterole=f`), cannot create databases (`rolcreatedb=f`), and has no privilege on databases other than `stickynotes`. The `postgres` superuser password (`POSTGRES_PASSWORD`) is still required for the image's first-init bootstrap and for operator ad-hoc maintenance (`docker exec -it <container> psql -U postgres`), just not for the app's runtime connection.

  **Operator action required (existing deployments).** docker-entrypoint-initdb.d only runs on fresh volume init, so existing deployments must create the role manually and transfer table ownership ONCE before redeploying:

  ```bash
  # 1. Set STICKYNOTES_APP_PASSWORD in .env (a fresh 32-char random string is fine).
  # 2. Run this from the existing deployment host:
  docker compose exec postgres psql -U postgres -d stickynotes <<'SQL'
    CREATE ROLE stickynotes_app WITH LOGIN PASSWORD 'paste-STICKYNOTES_APP_PASSWORD-here';
    GRANT USAGE, CREATE ON SCHEMA public TO stickynotes_app;
    ALTER TABLE board OWNER TO stickynotes_app;
    ALTER TABLE note OWNER TO stickynotes_app;
    ALTER FUNCTION archive_old_notes() OWNER TO stickynotes_app;
  SQL
  # 3. docker compose up -d (recreates the app container with the new DATABASE_URL).
  ```

  Fresh deployments (operators wiping the data volume or starting from scratch) get the role created automatically by the init script - no manual step needed.

- **Identity moved from a JSON cookie to a server-side session keyed by an opaque cookie-id.** Pre-fix, the identity cookie was plain JSON; the `/demos/denials` org ACL is keyed off `userData.org` which derives from this cookie, so any browser-side attacker who controls their own cookie can switch orgs at will. Considered HMAC-signing the payload (and shipped a prototype), then refactored to the canonical session-store pattern: the cookie is now a 128-bit opaque base64url session-id (~22 chars), and the actual identity (`id`, `name`, `color`, `org`) lives in Redis under `identity-session:<id>` as a hash with a 30-day sliding TTL. Forgery requires guessing a 128-bit random id (computationally infeasible). Compared to HMAC, this pattern gains: trivial per-user revocation (`DEL identity-session:<id>`), trivial field mutation (`HSET identity-session:<id> org globex` for the org-switch endpoint), and no long-lived shared secret to rotate or distribute across replicas. New module `$lib/server/identity-session` exports `lookupSession`, `createSession`, `updateSessionField`, plus `tryParseLegacyJsonCookie` for one-shot migration of pre-this-change visitors (their displayed name carries over). Wired through `+layout.server.js`, `hooks.ws.js`, `api/demos/set-org/+server.js`. The `COOKIE_SECRET` env var added in the earlier iteration is removed - the new pattern needs no secret. svelte-check passes with zero errors.

- **`/metrics` endpoint gated by `METRICS_SCRAPE_TOKEN` when set.** Pre-fix, the metrics endpoint was always reachable. Fix: when the env var is set, the handler requires a matching `X-Scrape-Token` header and 401s otherwise. When unset (default), the endpoint stays open - no behavior change for existing deployments. The endpoint's own comment already recommended gating; this implements it. `.env.example` documents the option.

- **Webhook secret fails closed in production.** `src/live/demos/news.js` previously fell back to a hardcoded `'demo-news-secret'` string when `DEMO_NEWS_WEBHOOK_SECRET` was unset, including in production - so the secret used to verify HMAC-signed webhook events was a value checked into the repo. Fix: the fallback now throws at module load when `NODE_ENV === 'production'`. Dev keeps the same fallback so a fresh checkout works without env setup.

- **Postgres bound to `127.0.0.1`.** Pre-fix, `docker-compose.yml` exposed Postgres on `5432:5432` (= `0.0.0.0:5432` on the host); operators with permissive host firewalls had a direct DB connection surface from any peer. Fix: port mapping changed to `127.0.0.1:5432:5432`. The app continues to reach Postgres via the docker bridge network (DNS name `postgres:5432`, see the network refactor below). External `psql -h <host>` from another machine is now blocked; operators run `docker compose exec postgres psql ...` or open a sidecar tunnel when DB access from the host machine is needed. Mirrors the docs repo's pre-existing 127.0.0.1 bind.

- **App container no longer uses `network_mode: host`.** Pre-fix, the app shared the host's network namespace and connected to redis/postgres at `127.0.0.1:6379` / `:5432` (the host's loopback). This works but couples the app to the host's network stack and conflicts with the localhost-bind changes (the loopback `127.0.0.1:6379` mapping on the redis service was bypassed by host networking - the app was hitting redis via the host's docker-proxy port mapping anyway). Fix: drop `network_mode: host`, publish port 443 explicitly via `"443:3443"` (container listens on 3443 as the non-root `node` user; docker-proxy handles the host-side 443 binding), and resolve redis/postgres via the docker bridge network's embedded DNS (`redis:6379`, `postgres:5432`). **Operator action required**: this is a coordinated networking change. Verify in staging that TLS handshake completes on https://your-domain before deploying to production. Cert volume mount (read-only at `/etc/letsencrypt`) is unchanged. Performance: one extra docker-proxy hop on inbound TLS, negligible for WebSocket/SSE-shaped workloads.

- **App container runs as the unprivileged `node` user.** Pre-fix, the demo's Dockerfile had no `USER` directive, so the app ran as root inside the container - giving any RCE inside node access to the full container's filesystem and capabilities. Fix: install `gosu`, copy a new `entrypoint.sh` that (a) copies the Let's Encrypt privkey (mode 0600 root) into a node-readable location and rewrites the SSL_CERT/SSL_KEY env vars to point at the copy, (b) execs `gosu node node build` to drop privileges before the app starts. Mirrors the docs repo's pattern. The image's port stays at 3443 (non-privileged) so no `cap_net_bind_service` is needed; docker-proxy handles the host:443 binding. **Operator action**: ensure your deployment workflow runs `docker compose build` to rebuild the image with the new entrypoint; the running container needs replacement.

### Changed

- **Identity cookie now has explicit `secure: !dev` and `sameSite: 'lax'`.** Previously the `cookies.set('identity', ...)` calls in `+layout.server.js` and `api/demos/set-org/+server.js` set `path` / `maxAge` / `httpOnly` but relied on SvelteKit defaults for `secure` and `sameSite`. SvelteKit's defaults are reasonable but explicit beats implicit; this future-proofs against a SvelteKit default-flip and makes the intent visible at the call site. `secure: !dev` means cookies require HTTPS in production but are allowed over HTTP in dev mode where the dev server runs at localhost.

- **`build.sourcemap: false` set explicitly in `vite.config.js`.** Vite's default depends on env/mode and could swap to `true` under a debug build path. Pinning to `false` prevents a future config drift from leaking server-source maps into the production bundle.

- **Docker base images pinned by digest.** `node:22-trixie-slim`, `postgres:17-alpine`, and `redis:7-alpine` in `Dockerfile`, `Dockerfile.postgres`, and `docker-compose.yml` are now suffixed with `@sha256:<digest>` so reproducible rebuilds cannot accidentally pull in a re-tagged base image. Bump the digests manually when the operator decides to pull in upstream security fixes; the existing `docker compose build` does not auto-resolve to newer image versions once pinned.

- **Production image installs only runtime dependencies.** Pre-fix, the production stage copied `node_modules` from the build stage, carrying every devDep (vite, svelte-check, playwright, etc.) into the runtime image. Fix: the production stage now runs `npm ci --omit=dev` directly against the same `package-lock.json`, then copies only the build artifacts (`/app/build`). Net result: a smaller image, zero devDeps shipped, and no chance of a future test/build tool getting executed at runtime. The build stage still installs full deps (it needs vite to build).

- **Redis bound to `127.0.0.1` and supports optional `REDIS_PASSWORD` AUTH.** Pre-fix, `docker-compose.yml` ran redis with `--protected-mode no` AND port mapping `6379:6379` (= `0.0.0.0:6379` on the host), making the cache directly reachable from any peer with network access to the host. This was a real exposure for deployments where the host firewall doesn't block 6379. Fix: (a) port mapping changed to `127.0.0.1:6379:6379` so only the host can reach redis, (b) `--protected-mode no` dropped (no longer needed, and keeping the default fail-closed posture is a defense layer for future misconfigurations), (c) the redis service's `command` now branches on `REDIS_PASSWORD`: when set, starts with `--requirepass`; when unset, starts unauthenticated (preserves existing-deployment behavior - no operator action required at upgrade time). The app's `REDIS_URL` mirrors with `redis://:${REDIS_PASSWORD:-}@127.0.0.1:6379`. Healthcheck also adapts. `.env.example` documents the option. Operators wanting AUTH set `REDIS_PASSWORD` in `.env` and recompose. Existing deployments without the variable keep working unchanged but now without the public 6379 surface.

- **`POST /api/demos/set-org` rejects cross-origin requests at the application layer.** SvelteKit's built-in CSRF check (in 2.59.x and earlier) fires only on form-content-types: `application/x-www-form-urlencoded`, `multipart/form-data`, `text/plain`, and SvelteKit's binary-form type. JSON POSTs are skipped by intent - the framework relies on browser CORS preflight + the `sameSite: lax` cookie attribute to defend cross-site CSRF for JSON. Both layers already protect this endpoint in practice (the identity cookie is sameSite: lax; no permissive CORS headers are set), but a future cookie-attr regression (sameSite: none) or a non-browser client bypassing CORS would reopen the gap. Defense-in-depth: the handler now reads `request.headers.get('origin')` and errors 403 if non-null and non-matching `url.origin`. Same-origin requests (the only legitimate use of this endpoint - the `/demos/denials` org-picker) continue to work unchanged.

- **`.gitignore` now excludes `*.pem`, `*.key`, `*.crt`, `*.pfx`, `*.p12`.** Pre-fix, only `.env*` was ignored - so Let's Encrypt artifacts (`fullchain.pem`, `privkey.pem`, `cert.pem`), self-signed dev certs from `init-certs.sh`, and Windows certificate bundles (`.pfx`, `.p12`) would slip into a commit on `git add .` from the wrong terminal. None are currently tracked (verified via `git ls-files | grep -iE '\.(pem|key|crt|pfx|p12)$'`), so the change is preventative rather than remediating - no historical commits need scrubbing. The same patterns landed in the docs repo's `.gitignore` under the same date.

- **`e2e/destroyer-standalone.js` no longer disables TLS verification process-wide.** Pre-fix, the script set `process.env.NODE_TLS_REJECT_UNAUTHORIZED = '0'` at module load, which disables certificate verification for EVERY subsequent TLS handshake in the process - not just the destroyer's own fetch calls. The WebSocket open at line ~50 already used a scoped `rejectUnauthorized: false` per connection; the global mutation was the remaining bypass. A future maintainer adding a fetch to a third-party endpoint (a metrics push, a webhook callback, anything) would unknowingly skip cert verification on that endpoint because the global toggle was still set. Fix: import `Agent` from `undici` (Node's bundled HTTP client; added as devDependency so the Agent class is reachable via public ESM import), construct a single `insecureDispatcher = new Agent({ connect: { rejectUnauthorized: false } })` for this script's two `fetch` calls (`getBoardId` and `checkServer`), and remove the global env mutation. Each fetch now passes `{ dispatcher: insecureDispatcher }`. The destroyer's behavior against self-signed certs is unchanged; what changed is that the bypass is now bounded to the two endpoints the destroyer actually hits.

### Changed

- **All six top-level shell scripts (`deploy.sh`, `init-certs.sh`, `renew-certs.sh`, `reset-all.sh`, `reset-db.sh`, `reset-redis.sh`) switched from `set -e` to `set -euo pipefail`.** Plain `set -e` catches only direct command failures in straight-line code; it misses (a) failures in the left side of a pipeline (the `false | tee` shape - the script proceeds even though the upstream errored) and (b) unset-variable references (a typo like `$DOAMIN` silently expands to empty string and feeds the empty string into `docker compose exec`). `set -u` (nounset) makes the typo error out; `pipefail` propagates pipeline failures. Audited each script for compatibility before flipping: the only scripts that read environment vars are the reset trio (`${CONFIRM:-}` is `set -u`-safe) and `init-certs.sh` (`${1:?...}` / `${2:?...}` are also `set -u`-safe by design). Pure `docker compose` driver scripts with no variable reads inherit the safer semantics for free.

### Security

- **`reset-all.sh`, `reset-db.sh`, `reset-redis.sh` now require `CONFIRM=yes` to run.** Pre-fix, anyone with `docker exec` access (or shell access to the operator's checkout) was one `./reset-all.sh` away from `TRUNCATE note, board CASCADE` plus `redis-cli FLUSHALL` against the running demo. A muscle-memory `./reset-` followed by a tab-complete in the wrong terminal pane would wipe production demo state with no second prompt. The scripts now check `[ "${CONFIRM:-}" != "yes" ]` before any destructive command and exit 1 with a usage hint; the new invocation is `CONFIRM=yes ./reset-all.sh` (or `./reset-db.sh`, `./reset-redis.sh`). The guard fires before `cd "$(dirname "$0")"` so even a script invoked from the wrong directory cannot proceed accidentally.

- **`reset-*.sh` excluded from the prod Docker image via `.dockerignore`.** Pre-fix, the scripts shipped inside the container at the workdir root (no `.dockerignore` rule excluded them) and were reachable via `docker exec demo-app bash /app/reset-all.sh`. Even with the new `CONFIRM=yes` guard at the script level, the principle is that operator tooling for tearing down dev data has no business being inside a production image - so the scripts are now stripped at build time by adding `reset-*.sh` to `.dockerignore`. Operators run them from the host checkout (where the scripts still live and the guard still applies).

## [0.4.0] - 2026-03-20

Aligns with svelte-adapter-uws 0.4.0, svelte-adapter-uws-extensions 0.4.0, and svelte-realtime 0.4.0.

### Breaking Changes

- **`hooks.ws.js` must export an `unsubscribe` hook.** Required by svelte-realtime 0.4.0. Without it, presence and cursor cleanup only happens on socket close, not on topic drop. Our implementation delegates to `presence.hooks.unsubscribe()`.
- **`close` hook signature changed.** The adapter now passes `{ platform, subscriptions }` instead of just `{ platform }`. Our hook now forwards the full context object to `presence.hooks.close()` and `cursor.hooks.close()` instead of destructuring.
- **Removed bare `export { presence, cursor }` from `hooks.ws.js`.** These module-level re-exports did nothing. All hook wiring is now explicit through named hook functions.
- **`cursor.remove(ws, platform)` replaced with `cursor.hooks.close(ws, ctx)`.** The extensions 0.4.0 cursor plugin exposes a `hooks` helper. Direct `.remove()` calls are replaced with the hooks pattern.
- **Dependency versions bumped.** `svelte-adapter-uws` from ^0.3.8 to ^0.4.0, `svelte-adapter-uws-extensions` from ^0.1.9 to ^0.4.0, `svelte-realtime` from ^0.1.7 to ^0.4.0. All three must be upgraded together.

### Added

- **`unsubscribe` hook** in `hooks.ws.js`. Fires the moment a client drops a topic (page navigation, stream teardown). Cleans up presence for that topic immediately instead of waiting for the socket to close. Users disappear from board presence bars the instant they navigate away.
- **Cursor snapshot on subscribe.** `cursor.hooks.subscribe()` is now called in the `subscribe` hook. When a user joins a board, they receive the current cursor positions of everyone already on that board instead of waiting for the next movement from each user.
- **Circuit breaker for Redis** via `createCircuitBreaker()` from `svelte-adapter-uws-extensions/breaker`. Wraps presence, cursors, pub/sub bus, and rate limiting. After 5 consecutive Redis failures, the breaker trips and operations fail fast. Probes again after 30 seconds. The app stays functional without Redis, just without cross-instance features. State changes are logged to the console.
- **`ctx.batch()` for arrangement actions.** Tidy, rearrange, shuffle, and group-by-author now publish all note updates plus the activity event in a single `ctx.batch()` call. Reduces Redis pub/sub round trips from N+1 to 1 when running multiple replicas.
- **`ctx.batch()` for cleanup cron.** Stale board deletions are published in a single batch instead of one-by-one.
- **Postgres advisory lock on cleanup cron.** With multiple replicas, only one acquires `pg_try_advisory_lock(900001)` and runs the cleanup. The others skip the tick. Prevents duplicate deletes and duplicate event broadcasts.
- **`tryAdvisoryLock()` and `advisoryUnlock()` in `db.js`.** Non-blocking advisory lock helpers. Return `true` immediately in dev mode (no Postgres) so crons run normally without a database.
- **Input validation guard for update payloads.** `validateBoardFields()` and `validateNoteFields()` now reject `null`, strings, arrays, and other non-object values with a clean `VALIDATION` error instead of throwing a raw TypeError.
- **First-load hint in dev mode.** A Vite plugin logs `[demo] First page load compiles all modules on demand -- expect 5-10 seconds. Subsequent loads are instant.` at server start so developers know to expect a slow first render.
- **Docker Compose runs 2 app replicas** again (was temporarily set to 1). Exercises the Redis pub/sub bus and advisory lock in production.

### Fixed

- **Startup race between migration and `ensureBoard`.** Previously, the `ALTER TABLE` migration and `ensureBoard('stress-me-out')` fired concurrently. If `ensureBoard` hit the database before the migration finished, it would fail with "column last_activity does not exist". Migration now completes before `ensureBoard` runs.
- **Dead migration code removed.** The `UPDATE board SET last_activity = created_at WHERE last_activity = created_at` query after the ALTER TABLE was a leftover from the initial backfill. It was a no-op since the column already existed with `DEFAULT now()`.
- **`moveCursor` called with undefined boardId.** The Canvas component could fire `moveCursor(undefined, pos)` if a pointer event fired before `boardId` resolved from route data. Added a `!boardId` guard in `flushCursor()`.
- **Stale E2E assertions.** `e2e/home.spec.js` expected "Sticky Notes" but the UI says "Svelte Realtime Demo". `e2e/board.spec.js` navigated home by clicking "Sticky Notes" text, now uses `a[href="/"]` which works regardless of viewport size.

### Under the Hood

- All arrangement actions (tidy, rearrange, shuffle, group-by-author) produce the same events in the same order. The only change is that they are sent as a single batch frame instead of N+1 individual publishes. No client-side changes needed.
- The `close` hook now delegates to `presence.hooks.close()` and `cursor.hooks.close()` instead of calling `presence.hooks.close()` and `cursor.remove()` separately. Same behavior, uses the standardized hooks pattern from extensions 0.4.0.
- The `subscribe` hook now calls both `presence.hooks.subscribe()` and `cursor.hooks.subscribe()`. Previously only presence was wired up. The cursor hook is a no-op for non-cursor topics.
- The circuit breaker has zero overhead when Redis is healthy. It only changes behavior after 5 consecutive failures.
- The advisory lock uses `pg_try_advisory_lock` (non-blocking). If the lock is held by another replica, the cron returns immediately without querying for stale boards.
- The `assertPlainObject` guard runs before any field access in `validateBoardFields` and `validateNoteFields`. No performance impact on valid payloads.
- Package version bumped from 0.0.3 to 0.4.0 to align with the upstream stack.
